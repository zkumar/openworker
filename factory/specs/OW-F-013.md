## The durable-workflow gap (recorded here per the register)

What exists today is NOT a durable workflow. Durability is assembled from four pieces in one
process:

- `coworker/ingress.py` (`IngressQueue`): the accepted payload is committed to SQLite before
  dispatch, so an accepted record survives a crash.
- `coworker/server/runstore.py` (`RunStore`): one SQLite row per run
  (`dispatched | gate | sealed | failed`), with attempts, backoff, and a generation that fences
  two writers apart.
- `coworker/dispatch/router.py` (`CapabilityRouter`): frame → capability → execute → learn,
  driven on a plain `threading.Thread` per item.
- `coworker/server/app.py` `_sweep_interrupted` (~line 285): a 5-second sweep thread that
  re-drives `dispatched` rows past their due time, re-dispatches unstarted ingress events, and
  retries undelivered receipts.

The gap: the coordinator itself is process-bound. If the sidecar dies, nothing is executing;
recovery depends on the next process start running the sweep, re-claiming rows and re-driving
runs by polling. There is no durable record of *where in the coordination* an item was (the
state enum approximates it), no durable timer for the human gate (a run can wait days only
because a poll loop keeps looking), and retry/backoff/fencing are hand-rolled. The owner's
intent in the register: the dispatcher becomes a long-lived durable workflow that coordinates
agents, never does the work itself, and waits for agents and humans to come back; durability
comes from Temporal. The sweep-plus-SQLite path stays as the no-infra fallback.

## Goal (phase 1 only)

An opt-in Temporal executor, selected by `OPENWORKER_EXECUTOR=temporal`, in which a
`WorkItemWorkflow` owns the coordination of one work item while every side effect stays in an
activity that wraps the EXISTING code paths (`CapabilityRouter`, `SessionManager.channel_*`,
`sign_channel_item`, `deliver_receipt`). With the env var unset, behavior is byte-identical to
today: no temporalio import, the sweep loop and SQLite journal untouched.

Stages, per the register: frame+capability → fabric pursue → signoff wait (a Temporal Signal
sent by the inbox approval resolution, with a slow poll-activity fallback timer) → sign +
receipt emit → learn.

## Acceptance

A1. `temporalio` is an optional extra (`openworker[temporal]`), imported only when
    `OPENWORKER_EXECUTOR=temporal` selects the executor. Env unset: no temporalio import
    anywhere in the dispatch path, and the local gate passes unchanged without temporalio
    installed.
A2. Fail closed, loudly: `OPENWORKER_EXECUTOR=temporal` with the extra missing, or with no
    Temporal server reachable, refuses at startup with an actionable error. Nothing silently
    falls back to the thread path.
A3. `WorkItemWorkflow` (new module under `coworker/dispatch/`) is deterministic and versioned
    (`WORKFLOW_VERSION`, after fabric RAF-021); it holds no side effect. Activities wrap the
    existing stages; the execute activity resumes via `CapabilityRouter.resume`, which looks
    before pursuing, so an activity retry never double-advances a run.
A4. The human gate is a Temporal Signal: `POST /v1/inbox/{id}/resolve` on a channel-run item
    signals the workflow (approve and deny both), and the sign activity then drives the
    existing `sign_channel_item` path (freeze → digest post → signoff), unchanged. A fallback
    poll activity on a durable timer closes the gate if a signal was lost. Fabric part11
    signoff stays the only human gate.
A5. Exactly one JSON receipt per work item, under replay: receipt emission goes through the
    existing derive-at-read builder (`build_receipt`) and keyed egress (`FileEgress`: one file
    per item ref), with RunStore's terminal state unchanged; re-delivery of the same item
    replaces its own file, never adds a second receipt. Never retry a 4xx: activity retry
    policies mark `FabricRefusal`-mapped errors non-retryable.
A6. With the env unset the sweep loop is untouched. With temporal selected, the sweep's
    `resume_interrupted_runs` call is skipped (the workflow owns resumption; two drivers would
    double-pursue); ingress re-dispatch and receipt retry keep running.

## Verification

V1. Negative (env unset), run BEFORE temporalio is installed in the venv: the local gate —
    the 8 files in `docs/known-failures.md` (41-test baseline recorded 2026-11-06; 47 after
    F-012) — passes unchanged, and a subprocess check proves `temporalio` is absent from
    `sys.modules` after importing and exercising the dispatch wiring.
V2. Fail-closed tests: executor selected + extra missing → actionable RuntimeError; executor
    selected + no server → loud failure, no thread fallback (new test file, additive; Temporal-
    path tests fail loudly when the dev server is expected, never skip silently).
V3. The binary criterion, recorded in `factory/GATES.md`: with `temporal server start-dev` up
    and `OPENWORKER_EXECUTOR=temporal` on an isolated sidecar (own `COWORKER_STATE_DIR`,
    `COWORKER_EGRESS_DIR`, spare port), dispatch one webhook demo item, `kill -9` the sidecar
    AFTER dispatch (run parked at the gate) and BEFORE signoff, restart it, approve the gate;
    the run completes with exactly one JSON receipt and the candidate content hash observed
    before the kill (the receipt's `signed_body_sha256` and the fabric chain's last sealed
    envelope at the gate) equals the one signed.

## Out of scope

(existing backlog item, used as-is for the joined run).

## Escalations (factory/config.md "Always escalate", accepted with the feature approval)

- "adds, removes or upgrades a dependency": `temporalio` as an optional extra; the `temporal`
  CLI (brew) as dev tooling for the gate.
- "changes evidence emission or receipt integrity": the receipt activity re-uses the existing
  emission path unchanged; V3 proves exactly-one receipt and an unchanged receipt body vs
  receipt-digest v1.0.0 (fabric `9fa5c92a4e552fbf45886921e331db6cc8799f1c`, PR
  zkumar/regagentic-fabric#58).
